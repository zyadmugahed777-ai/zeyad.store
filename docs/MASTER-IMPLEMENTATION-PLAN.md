# ZeyadStore — Master Implementation Plan

Executes the findings in `CRITICAL-FINDINGS.md` and the per-area audits (`BACKEND-AUDIT.md`, `ADMIN-AUDIT.md`, `MEDIA-AUDIT.md`, `NAJM-AUDIT.md`, `SQLITE-LEGACY-AUDIT.md`). Roughly 58 tasks (see `IMPLEMENTATION-TASKS.md`) across 14 waves, ordered by dependency in `DEPENDENCY-GRAPH.md` — not by symptom severity, because the async contract and the SQLite→Postgres shim sit underneath nearly everything else.

## Wave structure

**Critical path**: W0 → W1 → W2 → W3 → W7 → W13. Waves 4, 5, 8 can run in parallel after W2. Wave 9 needs W3. Waves 6 and 10 need W5/W2 respectively. Wave 11 is broadly parallel; Wave 12 must be last.

## Constraints (apply to every task)

- No redesign — preserve current UI/UX and visual identity; frontend edits only where a bug blocks existing functionality, minimally.
- Human-approval gates: schema changes, data migrations, credential changes, flipping `DATABASE_TYPE`, destructive operations, financial-rule changes.
- Financial changes require Δ = 0.0000 reconciliation against `backend/tests/golden-master-baseline.json`.
- Engineering independence: if code inspection shows a better/safer solution than what the audit suggested, use it — current code + runtime behavior + DB state outrank the historical audit text.

## Process per task

1. Read only the relevant audit section + affected files (targeted, not a full rescan).
2. Confirm root cause against current code before editing.
3. Implement the minimal correct fix.
4. Test the change; run only related tests.
5. Check for regressions and (where relevant) DB integrity.
6. Confirm SQLite isn't back in the runtime path for anything this task touched.
7. Update task status in `IMPLEMENTATION-TASKS.md`.
