# سياسة تغييرات بيئة الإنتاج وبوابات الأمان (PRODUCTION CHANGE POLICY)
**مشروع:** زياد للتجارة (ZeyadStore)  
**الهدف:** تحديد حدود الأمان التشغيلي مع منح Claude كامل الاستقلالية في الإصلاح البرمجي والتطوير.

---

## 1. فلسفة الأمان التشغيلي (Safety vs. Autonomy)

تم تصميم هذه السياسة لتمكين Claude Code من العمل كمهندس إنتاج مستقل، حيث يمكنه فحص وإصلاح وتطوير وإعادة هيكلة الكود بحرية وسرعة، مع حماية أصول وقواعد بيانات الإنتاج الحساسة من أي ضرر غير مقصود.

```
┌────────────────────────────────────────────────────────┐
│ 🟢 تغييرات مستقلة (AUTONOMOUS EXECUTION)               │
│ إصلاح الأخطاء (Bug Fixes) | إعادة الهيكلة (Refactor)  │
│ تحسين الاختبارات | التشخيص | ضبط الـ Services والـ API  │
└───────────────────────────┬────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────┐
│ 🔴 بوابات الموافقة البشرية (HUMAN APPROVAL GATES)       │
│ Schema DB في الإنتاج | ترحيل بيانات | تغيير Credentials │
│ تغيير DATABASE_TYPE في الإنتاج | حذف جداول / بيانات     │
└────────────────────────────────────────────────────────┘
```

---

## 2. تصنيف التغييرات (Change Categories)

### 🟢 الفئة الأولى: تغييرات ينفذها Claude باستقلالية تامة (Autonomous)
لا تتطلب هذه التغييرات موافقة بشرية مسبقة، ويملك Claude كامل الصلاحية في تشخيصها وتطبيقها واختبارها:
1. **إصلاح الأخطاء البرمجية (Bug Fixing):**
   - إصلاح مشاكل الـ Async/Await والمسارات في `routes/` و `services/`.
   - إصلاح التناقضات بين الفرونت إند والباك إند.
   - تصحيح أخطاء الجلسات والسلة والبحث والتحقق من المدخلات.
2. **إعادة الهيكلة وتحسين الكود (Refactoring & Code Quality):**
   - إعادة كتابة أو تحسين دوال الـ Repositories أو الـ Services لتحسين الأداء أو النظافة.
   - إزالة الكود الميت وتحسين بنية ومعمارية الملفات.
3. **تحسين وتطوير الاختبارات (Testing & Verification):**
   - كتابة Unit Tests و Integration Tests و E2E Tests.
   - تشغيل أدوات قياس الأداء (Latency profiling).
4. **تحسين أدوات وسلوك مساعد المبيعات "نجم" (AI & Tools):**
   - تحسين الـ Prompts، ضبط أدوات العملاء، وتحسين معالجة الـ Fallback.
5. **التشخيص وقراءة السجلات والتحديث التوثيقي:**
   - قراءة السجلات والاستعلامات التشخيصية للقراءة فقط وتحديث ملفات التوثيق.

---

### 🔴 الفئة الثانية: تتطلب موافقة بشرية صريحة (Human Approval Required)
تتطلب هذه العمليات عرض الخطة على المهندس المشرف والحصول على موافقته قبل التنفيذ:
1. **تغيير هيكل قاعدة بيانات الإنتاج (Production Database Schema Change):**
   - تنفيذ `ALTER TABLE`, حذف أعمدة، أو تغيير قيود المفاتيح الأساسية/الأجنبية على سيرفر الإنتاج.
2. **ترحيل أو تنظيف جماعي للبيانات (Mass Data Migrations):**
   - تشغيل سكربتات لتعديل جماعي لبيانات العملاء أو الأسعار في قاعدة الإنتاج.
3. **تغيير بيانات الاعتماد والمفاتيح في الإنتاج:**
   - تدوير كلمات مرور قواعد البيانات، `SESSION_SECRET`, أو مفاتيح الـ API المزودة في الإنتاج.
4. **تغيير محرك قاعدة البيانات النشط في الإنتاج:**
   - التبديل التشغيلي بين `DATABASE_TYPE=postgres` و `sqlite`.
5. **العمليات التدميرية (Destructive Operations):**
   - تنفيذ `DROP TABLE`, `DROP DATABASE`, `TRUNCATE`, أو حذف ملفات النسخ الاحتياطية.
6. **تعديل القواعد المالية الحساسة دون موافقة:**
   - تغيير معادلات تحويل العملات الرسمية أو سياسات التسعير بدون طلب صريح.
7. **التحويل الرسمي أو التراجع في الإنتاج (Production Cutover / Rollback).**

## 3. صيغة طلب الموافقة البشرية (Approval Request Template)

عند الحاجة لتنفيذ عملية من الفئة الحمراء 🔴، يقدم Claude طلباً واضحاً للمشرف:

```markdown
### ⚠️ طلب موافقة تشغيلية لبيئة الإنتاج (Production Gate Request)
- **العملية المطلوبة:** [Schema Change / Data Migration / Credential Change / etc.]
- **المبرر الهندسي والسبب الجذري:** [شرح المشكلة وسبب الحاجة للعملية]
- **النطاق والملفات/الجداول المتأثرة:** [قائمة بالأصول المعنية]
- **خطة التراجع (Rollback Plan):** [كيف سنعود للحالة السابقة بأمان في حال حدوث خلل؟]
- **حالة الاختبارات:** [نتائج الاختبارات المعزولة المسبقة]
```
